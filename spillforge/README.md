# SpillForge

本地数据处理服务：排序 / 去重 / 关联三类作业并发运行，共享一块**很小的临时盘**。
执行器、资源账本、调度器和网页全部从零实现，只依赖 Python 3.11 标准库（`sqlite3` +
`http.server`）与原生 HTML/CSS/JS。

所有“落盘”都是真的文件写入。默认预算 16 MiB 磁盘 / 12 MiB 内存，可以压到几百 KiB，
用来观察分片、归并、停放和崩溃恢复——不是模拟进度条。

```
python3 -m spillforge serve                 # UI: http://127.0.0.1:<port>
python3 -m spillforge serve --port 8765 \
    --disk-budget 3145728 --memory-budget 262144
python3 -m spillforge selftest              # 28 个单测 + 7 个崩溃点
python3 -m spillforge crash-test mid_merge  # 单点故障注入
```

## 输入格式

UTF-8 文本，每行一条记录 `key<TAB>payload`。

* 排序：整行字节序（等价 `LC_ALL=C sort`）。
* 去重：保留排序后第一条，按整行去重。
* 关联：以第一个 TAB 之前的字节为 key，输出 `key<TAB>left payload<TAB>right payload`。
  关联结果是 **桶序/探测序**，不是排序输出——需要有序就再跑一个排序作业。
  排序与去重的结果则严格有序。

## 结构

| 模块 | 职责 |
| --- | --- |
| `store.py` | SQLite 持久化：作业、预留、工件、引用、检查点、租约、事件、账本日志。**先写工件的元数据行，再创建文件**，所以恢复永远能凭表重建事实。 |
| `ledger.py` | 资源账本。准入、预留、债务、停放缩减、工件计数、引用检查、删除、对账。 |
| `planner.py` | 采样后决定 `streaming` / `in_memory` / `merge` / `repartition` / `hash_join` / `hash_join_partitioned`。 |
| `executor.py` | 分片、k 路归并、重分区、哈希连接、分区连接；每步写检查点；命名故障点。 |
| `recovery.py` | 启动/按需恢复：对账、按案例重建、清理孤儿文件、tombstone。 |
| `scheduler.py` | 准入循环、三种策略、停放与退避、取消/恢复。 |
| `server.py` / `web/` | JSON API 与中文操作界面（1 秒轮询）。 |
| `selftest.py` | 无 pytest 的 `unittest` 套件与崩溃用例。 |

## 资源账本

### 三道闸门，而不是一把大锁

1. **准入预估**：作业在任何文件存在之前先申请一笔保守的磁盘/内存预留。
   预估取“计划峰值，或 2×输入 + 8 KiB”，再截到本作业上限。
2. **每作业上限**：`max_job_fraction × 磁盘预算`（默认 65%）。
   任何单个作业都不能独占整个卷。
3. **有界债务**：写超预估时先吃上限内余量，再吃“没有任何人预留”的空隙，
   且债务本身有上限（`debt_allowance_fraction`，默认 15%）。

准入份额 = `min(预算 − 已承诺 − 预留松动, 上限 [+ 已有作业的债务空间])`。

`reservation_slack`（默认 20%）是一块**故意不分配**的余量。没有它，一串估计精准的
作业会把预算占满，任何一点估计误差都会直接失败；有它，误差有地方吸收。

### 保留结果也占容量

成功的作业把结果标为 `kept`（可下载），它不再属于任何预留，但**仍是同一块卷上的字节**。
准入因此把 `kept` 计入已承诺：

```
global_gap = 预算 − 活跃预留 − 保留结果
```

否则一串小作业可以靠结果堆满磁盘，而每个预留都显示“还很空”。UI 上的
“已承诺合计 = 预留 + 保留结果”就是准入真正看的数；`purge` 立刻把这部分还回去
（`test_retained_results_consume_admission_capacity`）。

### 超额怎么处理

| 情形 | 行为 |
| --- | --- |
| 写超预留，上限内有空间 | `charge()` 自动补足，继续跑 |
| 上限内无空间，但全局有空隙 | 借有界债务，继续跑 |
| 两者都不够 | 抛配额异常 → 执行器转成 `BudgetPause` → 作业**停放**，不失败 |
| 计划峰值 > 本作业可能拿到的最大值 | 写盘前 `BudgetInfeasible`，带具体数字失败 |

最后一档很关键：在**写任何临时字节之前**就算出“这个计划不可能放得下”。
否则就是一个大作业慢慢把盘写到接近满，再以晦涩的方式失败。失败信息会给出
计划峰值、预算、作业上限、债务上限和保留结果占用。

停放时预留会**缩到当前真实占用**，多出来的估计立刻还给全局池，其它作业可以立刻准入；
停放的任务保留已封好的分片，按指数退避（1s → 2s → … 封顶 30s）自动重试。
连续 12 次停放且**字节数毫无增长**才判定失败；只要还在写出新分片，就视为收敛、继续等。

## 引用安全：绝不删除别人正在读的中间结果

`artifact_refs` 是唯一的所有权记录。删除工件的流程是：

1. 在**同一个事务**里检查引用数，并把状态从 `complete` 改成 `reclaiming`；
2. 事务外 unlink；
3. 再开一个事务落成 `deleted` 并记负的实际字节。

所以“没有引用”与“决定删除”是原子的。进程死在第 2 步，下次对账看到 `reclaiming`
会补做 unlink；文件已消失也一样收敛到 `deleted`。

归并期间输入分片额外持有 `merge_input` 引用（`_open_runs`），归并结束才在 `finally`
里释放。取消或回收撞上正在读的归并时，`reclaim_job` 返回 `False`、**保留预留**并把
清理延后，由周期性对账线程重试——宁可短暂多占字节，也不会在账本上说“空间已空”
而文件还在。`test_no_live_intermediate_is_deleted_under_pressure` 在 1.5 MiB 预算下
跑 4 个并发作业，用采样线程断言“任何仍有引用的行都未被删除”，并要求最终账本归零。

`ledger.release_job()` 在仍有未回收工件时**拒绝释放**。这是刻意的：调用方漏删文件时
应该炸出来，而不是静默泄漏字节。

### 清理也要认领“哪一次运行”

取消和恢复会竞争同一个工作目录，所以每次派发都会把作业的 `run_epoch` 加一，清理线程
捕获它被派发时的值。`reclaim_job(expect_epoch=…)` 在删任何文件前先比对：若作业已经
在新代号下重新运行，这次清理立即让路（事件 `cleanup_superseded`）——否则“取消后立刻
恢复”会把新执行器的检查点和分片删掉。另外，`_dispatch` 的 CAS 若因 `cancel()` 抢先
改状态而失败，它会自己补上收尾，不会留下永远停在 `cancelling` 的作业。
这两个竞态各有一个 40 轮循环的回归测试（`selftest.py`）。

发布提交点之前还有最后一次停止检查：一旦作业行写上 `result_path`，结果就可下载，
取消只能变成“删结果”；在此之前取消总能生效。

## 策略选择：分批归并还是重分区

采样（头部 + 6 个随机偏移）给出平均行长、估计记录数、key 频率、重复率和**相邻有序比例**。
决策顺序：

1. 样例基本有序 → `streaming`：一遍流过输入直接写结果，零分片。
2. 输入能放进作业内存片 → `in_memory`。
3. 否则 `merge`：按内存预算切分片、各片排序，再做**分批归并**：
   每轮最多打开 `fan_in` 个分片（同时受文件描述符、归并内存和 32 的上限约束），
   把每一组合并成一个中间工件，直到只剩一组，最后一轮才写 `result.srt`。
   每完成一组就提交检查点，崩溃只重做当前这一组，已合并的中间结果不重算。
4. 只有当**分片数超过 `max_runs_per_job`**，且重分区峰值仍在上限内，才改用
   `repartition`（按整行哈希取模）。

第 3 条是端点不是装饰：870 个分片、`fan_in=2` 时执行器开 10 轮归并，任何时刻
最多 2 个只读句柄（`ulimit -n 64` 下实测通过）；若一次性打开全部分片，1024 个 fd 的
机器会在几百个分片时 `EMFILE`，归并内存也从"按 fan-in"退化成"按分片数"。
计划里的 `merge_passes` 与实际执行的轮数会在作业统计里对照显示（`planned_merge_passes`）；
两边都把**写最终结果的那一轮**算进去，所以单轮归并也显示 `1/1`，而不是 `0/1`。

第 4 条是刻意的：重分区是**分片数**的解药，不是**磁盘峰值**的解药——它要多读多写一遍，
峰值只会更高，绝不会更低。把它当“省磁盘”手段是错的，代码里也这么写了。

关联：构建侧是否放得下（`字节×1.8 + 记录数×96`，刻意悲观）决定 `hash_join` 还是
`hash_join_partitioned`；构建侧热 key 占比 ≥5% 会给出警告并倾向分区，避免热 key
把整个构建侧拖进内存。

**关联的输出不是输入的复制。** 两侧重复 key 会相乘：400 个 key、每侧 20 条重复，8 千行
输入会输出 16 万行，是输入的 150 倍。计划因此单独估计结果行数
`L·R / 匹配 key 数`，其中 key 基数用 Good–Turing 覆盖率（`D ≈ 观测 key 数 / (1 − 单次出现数/样本量)`）
外推。这一项既要在重复 key 时放大到 150 倍，又不能在 key 空间宽时把 2 万 key 误判成
2 千——朴素地按 `样本量/总行数` 缩放会把两个方向都算错。计划峰值必须包含这份结果，
否则作业会在写结果时越界、停放，然后因为额度从不增长而永远停放。
`test_join_result_size_is_estimated_from_key_multiplicity` 覆盖了这一点。

分区关联按 **key**（第一个 TAB 之前）取哈希，而不是整行：匹配发生在 key 上，若按整行
哈希，`k<TAB>left` 与 `k<TAB>right` 会落进不同桶，匹配对永远不会相遇。排序/去重分区
仍然按整行哈希——那里的结果只是所有行的重排，任意稳定切分都正确。
`test_partitioned_join_matches_on_the_join_key` 覆盖了这个回归。

同一个结果路径被重新创建时必须替换上一轮的 `open` 记录，而不是并排累加。停放的作业
恢复后会用 `open("wb")` 重写 `result.joined`；早先每轮都新增一行账目，16 轮之后账本
声称 4 MB 而磁盘上只有 300 KB，作业再也不可能被准入。
`test_recreating_an_open_artifact_at_the_same_path_does_not_double_count` 覆盖了这一点。

## 吞吐 vs 公平

三种策略都显式实现且可测（`SchedulerTests`）：

* **吞吐优先** `throughput`：单通道 FIFO，一次只跑一个 spiller。
  顺序 I/O 最省、归并换入换出最少，总耗时最短；代价是长作业前面的小作业必须干等。
* **公平优先** `fairness`：最多 `max_concurrent_jobs` 个并发 spiller，按**估计工作量最短优先**
  排队，并带**老化**：等待超过 `fairness_aging_seconds`（默认 20s）的作业提升到队首。
  小作业低延迟完成；大作业不会饿死；代价是 I/O 交错，单作业吞吐下降。
* **自适应** `adaptive`：磁盘压力低于高水位时按 FIFO 单通道，接近上限时切公平多通道——
  此时尽快完成小作业才是最快腾出空间的方式。

这是本项目的核心取舍：**单通道顺序 I/O 的单位时间吞吐更高，但作业完成时间的方差极大；
多通道交错 I/O 牺牲一些总吞吐，换来可预测的排队延迟。** 停放机制让这个取舍不至于
变成“一个大作业饿死所有人”：估计错误的作业只会拖慢自己，被它让出的容量立刻可用。

## 崩溃恢复

检查点写在 SQLite 里，与工件的行同库提交。四类要求覆盖的边界：

| 故障点 | 崩溃时磁盘上有什么 | 恢复动作 |
| --- | --- | --- |
| `after_run_complete`（分片写完） | 一组 `complete` 分片，检查点 `merging` | 保留全部分片，只删半成品结果，从检查点重排归并 |
| `mid_merge`（归并一半） | 分片 + `open` 的部分结果 | 删部分结果、保留分片，重做归并 |
| 分批归并的 `mid_merge`（写到中间工件时崩） | 已提交的当前分片集 + 一个 `open` 的 `merge_tmp` | 只删这个半成品中间文件，从检查点记录的**当前分片集**继续当前这一轮，不重算已合并的组 |
| `before_budget_release` / `after_publish_before_release`（发布后、释放前） | `kept` 结果，作业行已有 `result_path` | 不重算：丢掉输出引用、回收分片、补释放预留 |
| `after_final_write_before_seal`、`during_scatter`、`after_bucket_sorted` | 未封口或部分桶 | 按检查点阶段选择重扫/重排，孤儿文件由对账清除 |
| `during_partition`、`mid_join_bucket`（关联分区/逐桶连接中崩） | 已完成的分区 + 一个 `open` 结果 | 保留分区工件，删半成品结果，按检查点 `phase=join` 直接从分区继续，不重新分区 |

恢复流程固定先做三件事：清空租约、按 `stat()` 对账每个工件的真实字节、逐作业分类。
对账会把“崩溃前写了但没记账”的字节补上（必要时用有界债务），把消失的文件标成
`deleted` 并记事件，把 `reclaiming` 残留的 unlink 做完。

`python3 -m spillforge selftest` 对七个故障点逐一验证：崩溃状态可达、恢复报告正确、
**恢复后的输出与不间断运行逐字节相同**、账本最终 `reserved=0 / actual=0`、无残留工件。
其中第五个用例专测分批归并：8 KiB 内存预算强制产生数百个分片与多轮归并，在中间工件写到
一半时注入 `mid_merge`，验证恢复只丢弃半成品中间文件、从检查点的当前分片集续跑；
最后两个用例用真正的关联作业（`hash_join_partitioned`）验证分区阶段与逐桶连接阶段的恢复——
这两个故障点在排序作业里永远触发不到，早先用排序去跑只会得到“没有崩溃”的空通过。

## 网页

* 磁盘/内存仪表：预算、预留、实际占用（`stat` 校准）、保留结果、已承诺合计、可准入、
  卷剩余，标出高水位线。
* 提交面板：真实拖拽上传或合成数据（记录数 / 倾斜 / 是否已排序），选 sort/dedupe/join，
  join 需要第二个文件；可选故障注入点。
* 作业表：状态、阶段、计划理由、预留与债务、RSS、迷你进度条、取消/恢复/下载/删除结果。
* 账本日志（带余额快照）、事件流、上传列表、恢复报告、作业详情（计划估计、实际归并轮数与
  计划轮数的对照、检查点、工件与引用数、账本明细、结果预览）。

## 已知边界

* 单进程、单写连接；SQLite 串行化所有元数据写入。这是演示规模下的刻意选择。
* 上传文件不计入临时预算（它们是用户数据），由 `max_upload_bytes` 单独限制。
* 内存预算是“排序缓冲”的预算，不是 RSS 断言；UI 单独显示进程 RSS。
* `merge_input` 引用意味着“取消后仍被读取的作业”可能短暂保留预留；这是正确的方向：
  先保证不删正在读的文件，再尽快归还额度。
* 内存预留是“可见性 + 软预算”，申请量取 `min(作业内存上限, 当前可准入份额)`。
  计划本身仍按上限设计缓冲区，所以极小的内存预算会换来更多分片和更多归并轮数，
  而不是把作业拒之门外。
* 分批归并临时文件的峰值是“全部输入 + 一个分片输出”，计划里已计入这一项；
  轮数越多 I/O 越多，这是低内存换来的真实代价，不是可以隐藏的开销。
